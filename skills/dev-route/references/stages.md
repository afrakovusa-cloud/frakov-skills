# Этапы маршрута

Источник: стрим Сергея Шимы (8 этапов) + 6 поправок разбора. Здесь — как этап делается. Пункты-чекбоксы этапов живут
в шаблоне `route-template.md`, не здесь.

Все файлы проекта (`BRIEF.md`, `PRD.md` …) лежат в корне папки проекта рядом с `ROUTE.md`.
Этапы 1–5 — каждый в новой сессии: между сессиями передаётся файл, не история чата.

## 1. Голос → бриф
- Вход: голос пользователя (диктовка или голосовое), 10–30 минут про конечный результат. Стек не нужен.
- Делаешь: расшифровку → бриф без потерь и повторов. Разделы: результат; сценарии как конечное
  состояние глазами пользователя (Дано / Когда / Тогда); роли — для каждой «видит / делает / доступ к
  данным»; агент как пользователь (AX: что ему нужно, ключи, API); чего НЕ делаем.
- Выход: `BRIEF.md`. Пробел в брифе — вопрос пользователю, не догадка.

## 2. Исследование (только полный трек)
- Вход: `BRIEF.md`.
- Делаешь: готовые решения на GitHub (лицензия MIT / Apache 2.0, иначе не берём); блоги разработчиков
  по теме; продукты-аналоги через браузер (скилл `playwright`) — UX-отчёт и как устроена логика;
  поиск — веб-поиск агента. Чужой код до использования — проверить на секреты, сеть, скрытые команды.
- Выход: `RESEARCH.md` — таблица «что берём / откуда / лицензия» + «что не берём и почему».

## 3. Прожарка
- Вход: новая сессия + `BRIEF.md` (+ `RESEARCH.md`).
- Делаешь: скилл `grilling` (вызвать через Skill). Раундами по 3–5 вопросов, у каждого — рекомендованный ответ
  Факты ищешь сам, пользователю — только решения.
  Дави масштабом, сбоями, работой агента; «всё понятно» пользователя — не конец, конец — пустой фронтир.
- Выход: `GRILL.md` — решения по раундам. Ответ не нашёлся → пункт «открыт», не выдумывать.

## 4. PRD + словарь + философия + DoD
- Вход: `BRIEF.md`, `RESEARCH.md`, `GRILL.md`.
- Делаешь:
  - `PRD.md` — сценарии «Я как <роль> хочу <действие>, чтобы <цель>»; роли; масштаб (сколько
    пользователей / данных). У каждого сценария: критерий «прошёл / не прошёл», требование к скорости,
    как его прокликать на приёмке. Это поправка разбора: DoD закладывается до кода.
  - `CONTEXT.md` — словарь по `pocock/domain-modeling.md` + `CONTEXT-FORMAT.md`.
  - `PHILOSOPHY.md` — что важнее при конфликте (5–10 строк) и что проект не делает никогда.
  - ADR в `docs/adr/` — только по трём условиям из `pocock/ADR-FORMAT.md`.
- Пользовательскую часть PRD пользователь читает сам целиком; техническую проверяет этап 5.

## 5. Второе мнение (только полный трек)
- Вход: `PRD.md`, `RESEARCH.md`, `CONTEXT.md`, `PHILOSOPHY.md`.
- Делаешь: чистый субагент без истории чата, промпт — «найди упущенное: сценарии, сбои, масштаб,
  безопасность, роль агента, противоречия словарю. Не хвали». Есть доступ к другой сильной
  модели — лучше она: у моделей одного семейства общие слепые пятна.
- Выход: `REVIEW.md` — по каждому замечанию «принято → что поменяли» или «отклонено, потому что».

## 6. Чек-лист и сборка
- Вход: `PRD.md` + словарь + философия.
- Делаешь:
  - `CHECKLIST.md` — потоки: инфраструктура, каркас, ядро, модули, UI. Внутри — вертикальные срезы
    (сценарий целиком тонким слоем), не «сначала весь бэкенд».
  - Задание исполнителю — файл `tasks/NN-имя.md`: куда смотреть, что сделать, границы (что не
    трогать), DoD, как доложить. Исполнитель одноразовый — всё нужное в файле.
  - `AGENTS.md` проекта — указатель «что где лежит», ≤ 30 строк, не свод правил.
  - Журнал событий — в отдельный файл/таблицу, не только в логи (с него начинается разбор поломки).
  - Исполнитель по типу платформы (свой скилл сборки, если есть).
    Параллельные субагенты — только после «да» пользователя с прикидкой лимита.
- Сборка идёт там, где приложение будет жить: эмулятор / телефон / браузер.

## 7. Приёмка
- Тесты пишет не исполнитель: отдельный субагент-тестировщик по `pocock/tdd.md` (`tests.md`,
  `mocking.md`); швы для тестов согласовать с пользователем. Ссылки tdd.md на `codebase-design` и
  `code-review` — скиллов Покока у нас нет, пропускать.
- Где есть расчёты/парсинг — property-based тесты (библиотека сама подбирает странные входы).
- Тест краснеет на откате фикса — иначе пустышка.
- Критик (ещё один субагент) атакует тесты; ≤ 3 круга, дальше решает архитектор (ты) и говорит пользователю.
- Гейт объёма: `git diff --stat` против `CHECKLIST.md` — каждое изменение привязано к пункту;
  лишнее — убрать или в `BACKLOG.md`. Лишнее без спроса проходит все остальные гейты.
- Хук качества перед коммитом (линтеры, метрики) — если есть. Первый проект — замерить: что гейт
  поймал и что пропустил; не ловит ничего — не ставить дальше.
- E2E: каждый сценарий PRD прокликан — веб — через Playwright, Android — эмулятор.
  UI/UX пользователь смотрит глазами.
- Итог — сверка результата с критериями PRD: что готово, что под риском, что не проверено.

## 8. Длинная дистанция
- После MVP всё новое — в `BACKLOG.md`.
- Новая фича → `route.py init ROUTE-<фича>.md --track feature` (этапы 3, 4, 6, 7) и сверка с
  `CONTEXT.md` + `PHILOSOPHY.md`.
- В `BACKLOG.md` счётчик заплаток по модулю; 5 заплаток → перестроить модуль, не клеить шестую.
- Конец каждой сессии: отметить `ROUTE.md` → handoff-заметка (что сделано, что дальше, какие файлы) →
  `/compact`.
- Раз в неделю активной работы: почистить `AGENTS.md` проекта от устаревшего.
