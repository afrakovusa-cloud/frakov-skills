# Этапы маршрута

Источник: стрим Сергея Шимы (8 этапов) + 6 поправок разбора; таймкоды стрима — в скобках. Здесь — как этап
делается. Пункты-чекбоксы этапов живут в шаблоне `route-template.md`, не здесь.

Все файлы проекта (`BRIEF.md`, `PRD.md` …) лежат в корне папки проекта рядом с `ROUTE.md`
(фича — в своей папке, см. этап 8). Этапы 1–5 — каждый в новой сессии: между сессиями передаётся
файл, не история чата.

## 1. Голос → бриф
- Вход: голос пользователя (диктовка или голосовое), 10–30 минут про конечный результат. Стек не нужен.
- Делаешь: расшифровку → бриф без потерь и повторов. Разделы: результат; сценарии как конечное
  состояние глазами пользователя (Дано / Когда / Тогда); роли — для каждой «видит / делает / доступ к
  данным»; агент как пользователь (AX: что ему нужно, ключи, API); чего НЕ делаем.
- Выход: `BRIEF.md`. Пробел в брифе — вопрос пользователю, не догадка.

## 2. Исследование (только полный трек)
- Вход: `BRIEF.md`.
- Делаешь:
  - Готовые решения на GitHub. MIT — берём; Apache 2.0 — берём с указанием авторства; прочие
    лицензии — только смотрим, как устроено, код не копируем (24:13, 25:47).
  - Блоги разработчиков по теме; продукты-аналоги через браузер (Playwright) — UX-отчёт и как
    устроена логика; поиск — веб-поиск агента. Чужой код до использования — проверить на секреты, сеть, скрытые команды.
  - Книги по архитектуре темы (Фаулер и т.п.): выжимка принципов с агентом; часто нужна — скилл из выжимки (33:46).
- Выход: `RESEARCH.md` — таблица «что берём / откуда / лицензия» + «что не берём и почему» + книги.

## 3. Прожарка
- Вход: новая сессия + `BRIEF.md` (+ `RESEARCH.md`). Фича: `FEATURE.md` в её папке (голос пользователя
  про фичу → текст) + разбор кода, который фича трогает (выжимка или диаграмма модулей) — Шима сначала
  разбирается в коде, потом прожарка внутри репо (65:53).
- Делаешь: скилл `grilling` (вызвать через Skill) **вместе с** разделом «During the session» из
  `pocock/domain-modeling.md` — у Шимы это «grilling with docs» (16:27): термины оспариваются и
  записываются в `CONTEXT.md` по ходу прожарки, не пачкой потом. Поправка к `grilling`: **раунд — 3–5 вопросов**. Фронтир шире
  5 → задать 3–5 самых корневых, остальное в следующий раунд (у Шимы — по одному; 50 вопросов разом
  дают ответы наспех, 20:02). У каждого — рекомендованный ответ. Факты ищешь сам, пользователю — только решения.
  Дави масштабом, сбоями, работой агента; «всё понятно» пользователя — не конец, конец — пустой фронтир.
- Выход: `GRILL.md` — решения по раундам. Ответ не нашёлся → пункт «открыт», не выдумывать.

## 4. PRD + словарь + философия + DoD
- Вход: `BRIEF.md`, `RESEARCH.md`, `GRILL.md`.
- Делаешь:
  - `PRD.md` — сценарии «Я как <роль> хочу <действие>, чтобы <цель>»; роли; масштаб (сколько
    пользователей / данных). У каждого сценария: критерий «прошёл / не прошёл», требование к скорости,
    как его прокликать на приёмке. Это поправка разбора: DoD закладывается до кода. У каждой роли —
    сценарии и для агента с её правами (через API/ключ): «сценарии для агента, сценарии для
    пользователя» (61:39).
  - `CONTEXT.md` — словарь, начатый на прожарке: дочистить по `pocock/CONTEXT-FORMAT.md`.
  - `PHILOSOPHY.md` — что важнее при конфликте (5–10 строк) и что проект не делает никогда.
  - ADR в `docs/adr/` — только по трём условиям из `pocock/ADR-FORMAT.md`.
- Пользовательскую часть PRD пользователь читает сам целиком; техническую проверяет этап 5. В треке lite
  этапа 5 нет — техническую часть ловят тестировщик и критик на этапе 7.

## 5. Второе мнение (полный трек и фича)
- Вход: `PRD.md`, `RESEARCH.md` (у фичи его нет — `FEATURE.md` и разбор кода), `CONTEXT.md`, `PHILOSOPHY.md`.
- Делаешь: чистый субагент без истории чата, промпт — «найди упущенное: сценарии, сбои, масштаб,
  безопасность, роль агента, противоречия словарю. Не хвали». У Шимы — другая сильная модель (37:54):
  она видит, чего нет в нашем контексте. Есть доступ к другой сильной модели — лучше она;
  чистый субагент той же модели закрывает «вне контекста», но не «другие слепые пятна».
- Выход: `REVIEW.md` — по каждому замечанию «принято → что поменяли» или «отклонено, потому что».
- Принятое замечание меняет решение из `GRILL.md` → короткая прожарка только по нему (23:15).

## 6. Чек-лист и сборка
- Вход: `PRD.md` + словарь + философия.
- Делаешь:
  - `CHECKLIST.md` — потоки: инфраструктура, каркас, ядро, модули, UI. Внутри — вертикальные срезы
    (сценарий целиком тонким слоем), не «сначала весь бэкенд».
  - Дизайн (если есть UI) — до потока UI. Модель сама дизайн не придумывает — выходит «слоп» (63:05):
    4 варианта от случайного зерна (попроси модель сгенерировать случайную строку и строить от неё —
    иначе варианты одинаковые) → пользователь выбирает → экраны по PRD и ролям (64:19).
  - Задание исполнителю — файл `tasks/NN-имя.md`: куда смотреть, что сделать, границы (что не
    трогать), DoD, как доложить. Исполнитель одноразовый — всё нужное в файле. В каждом задании:
    - сделал шаг → отметь пункт в `CHECKLIST.md`; сделал что-то сверх задания → строка в `BACKLOG.md`,
      не молча (74:57) — лишнее ловится во время сборки, а не только на приёмке;
    - один файл — одна ответственность (большие файлы агент при поломке переписывает целиком, 59:21);
      ничего «на будущее» (YAGNI); повтор — вынеси, не копируй (DRY); проще — лучше (KISS).
  - `BACKLOG.md` — завести сейчас: в него пишут исполнители и гейт объёма.
  - `AGENTS.md` проекта — указатель «что где лежит», ≤ 30 строк, не свод правил.
  - Журнал событий — в отдельный файл/таблицу, не только в логи (с него начинается разбор поломки).
  - Исполнитель по типу платформы (свой скилл сборки, если есть).
    Параллельные субагенты — только после «да» пользователя с прикидкой лимита.
  - Модели по ролям (52:18): исполнитель может быть дешевле (субагент `model: sonnet`), тестировщик и
    критик — самая сильная доступная (`opus`).
- Сборка идёт там, где приложение будет жить: эмулятор / телефон / браузер.

## 7. Приёмка
- Тесты пишет не исполнитель: отдельный субагент-тестировщик. Из `pocock/tdd.md` (`tests.md`,
  `mocking.md`) берём, что такое хороший тест, швы (согласовать с пользователем) и анти-паттерны.
  Правило tdd.md «тест до кода» здесь не выполнимо (код уже написан на этапе 6) — его заменяет «тест
  краснеет на откате фикса». Ссылки tdd.md на `codebase-design` и `code-review` — скиллов Покока у нас
  нет, пропускать; рефакторинг — после зелёной приёмки отдельным заданием исполнителю, затем приёмка снова.
- Где есть расчёты/парсинг — property-based тесты (библиотека сама подбирает странные входы).
- Тест краснеет на откате фикса — иначе пустышка.
- Мутационный прогон, где есть логика (52:38): инструмент нарочно портит код (Python — `mutmut`,
  JS/TS — Stryker; ставится в проект), хорошие тесты обязаны покраснеть.
- Критик (ещё один субагент) критикует тестировщика, не исполнителя (53:34): покрытие логики не
  ниже 80%, тесты не подогнаны под код. Две петли:
  - **тесты плохие** → обратно тестировщику; спор тестировщик ↔ критик ≤ 3 круга (53:54), дальше
    решает архитектор (ты) и говорит пользователю;
  - **тесты нашли баг в коде** → новое задание исполнителю (`tasks/NN`) → тестировщик → критик (54:13).
- Гейт объёма: `git diff --stat` против `CHECKLIST.md` — каждое изменение привязано к пункту;
  лишнее — убрать или в `BACKLOG.md`. Лишнее без спроса проходит все остальные гейты.
- Хук качества перед коммитом (линтеры, метрики) — если есть. Первый проект — замерить: что гейт
  поймал и что пропустил; не ловит ничего — не ставить дальше.
- E2E: каждый сценарий PRD прокликан, включая сценарии агента (через его API/ключ) — веб — через Playwright, Android — эмулятор. UI/UX пользователь смотрит глазами.
- Итог — сверка результата с критериями PRD: что готово, что под риском, что не проверено.

## 8. Длинная дистанция
- После MVP всё новое — в `BACKLOG.md`.
- Новая фича → своя папка: `route.py init features/<фича>/ROUTE.md --name <фича> --track feature`
  (этапы 3, 4, 5, 6, 7). `GRILL.md`, `PRD.md`, `REVIEW.md`, `CHECKLIST.md` фичи — в её папке: забор
  проверяет их там, основные файлы проекта не затираются. Сверка со словарём и философией —
  основными `CONTEXT.md` + `PHILOSOPHY.md` проекта. После приёмки — сценарии фичи слить в основной
  `PRD.md`, новые термины — в основной `CONTEXT.md`.
- В `BACKLOG.md` счётчик заплаток по модулю; 5 заплаток → перестроить модуль, не клеить шестую.
- Конец каждой сессии (на любом этапе) — правило в SKILL.md: `ROUTE.md` → `HANDOFF.md` → `/compact`.
- Раз в неделю активной работы: почистить `AGENTS.md` проекта от устаревшего.
